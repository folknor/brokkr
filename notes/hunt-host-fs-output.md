# Host, filesystem and output hygiene report

I reviewed the source and documentation at `de29e1d6`. This was a static review. I made no filesystem changes and ran no builds, tests, or `brokkr` commands. The consequences below follow from the code paths cited.

I would rewrite the shared platform boundary. An invocation should hand commands a resolved environment and working directory, host probes with explicit failure states, a clock, owned storage locations, and an output sink. In particular, `env` should report the same decisions the runners and gates consume. The current design repeatedly asks the host the same question, then gives each caller its own fallback, interpretation, and wording.

## Environment, paths, and startup

- **Cargo home has two resolution implementations.** Both skip empty `CARGO_HOME` and `HOME` and fall back to the passwd home. `user_dirs` uses the process cwd for relative `CARGO_HOME` and leaves a relative `HOME/.cargo` relative. `rustflags` uses the Cargo child's cwd and joins both relative forms to it. The child and invocation may legitimately have different inputs. The precedence, empty-value handling, and normalization belong in one explicit-input resolver. A table test should cover absolute, relative, empty, missing, non-UTF-8, and passwd cases. [Invocation resolver](/home/folk/Programs/brokkr/src/user_dirs.rs:144), [child resolver](/home/folk/Programs/brokkr/src/rustflags.rs:527)
- **`HOME` has several meanings inside the same invocation.** The guard and brokkr share a resolver that accepts any nonempty value. A relative `HOME` can put the supposedly cross-project lock under different cwd-relative paths. XDG overrides must be absolute, but their fallback can still inherit that relative home. History's text redaction requires an absolute UTF-8 home. Results-server deploy requires an absolute home and uses a fixed `.config` path, even with `XDG_CONFIG_HOME` set. The passwd lookup also turns an undersized `getpwuid_r` buffer into absence without retrying. Resolve an absolute account context once, with explicit policy for each consumer. Test the same environment matrix across the binaries. [Shared lock paths](/home/folk/Programs/brokkr/src/user_dirs/paths.rs:13), [XDG and passwd](/home/folk/Programs/brokkr/src/user_dirs.rs:103), [redaction](/home/folk/Programs/brokkr/src/history.rs:706), [deploy](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:82)
- **The user-config report reconstructs part of startup.** Startup discards the attempted path on `NotFound`, including an explicitly named `BROKKR_USER_CONFIG` path. `env` calls the resolver again to display absence, and its tests compile out that branch's environment lookup. A typo in the explicit override silently drops the user's gates. Preserve a startup record with disabled, absent default, absent explicit, and loaded states. The existing config contract constrains a new refusal for the explicit case. A warning and a resolution-matrix test can expose it without changing what loads. - **Three paths can answer “where is target?”** The disk gate checks `<build root>/target` and a nonempty ambient `CARGO_TARGET_DIR`. `env` uses Cargo metadata, then prefers the host `target` key, which only affects its report. Actual invocations can get their locations from Cargo config, a separate build dir, or the recipe's injected environment. The gate can refuse a full default filesystem when the build writes elsewhere, or admit a build whose actual destination is full. `env` also labels low **data** and **scratch** mounts as places where locked commands refuse, even when the gate never probes them. Resolve the write destinations per operation and give the gate and report that plan. Test the host override, relative env, Cargo config, separate build dir, and worktree cases. ## Linux facts, clocks, and filesystem capacity

- **CPU counts disagree about what they count.** Inventory takes the first `cpu cores` in `/proc/cpuinfo` and labels it physical cores alongside a machine-wide processor count. A multisocket host can show a per-package numerator. The default cache probe groups by `(package, core_id)` while `budget = "cores"` uses sibling masks because dies can reuse core IDs. `env` labels the raw cache-domain count the parallel budget even when execution caps it by visible `cpu.max`, and reports “not detected” when execution will choose a fallback. Use one topology snapshot with separate machine, affinity, cache, and effective budget fields and test multisocket, repeated core IDs, and quota-limited containers. [CPU inventory](/home/folk/Programs/brokkr/src/host/cpu.rs:37), [topology policies](/home/folk/Programs/brokkr/src/cpu_topology.rs:112), [env budget](/home/folk/Programs/brokkr/src/env.rs:187)
- **The cache probe assumes `index3`, chooses the first usable domain, and doesn't place work there.** Cache indices, domain sizes, and CPU classes can vary. Missing `index3` gives a whole-affinity physical count, while a partially readable domain can give a partial count. The budget alone makes no claim about where Linux schedules the tests. CPU frequency and governor come from `cpu0` even when that CPU is offline, excluded, or unlike the CPUs running the work. Enumerate cache level and type, report which affinity and policies were observed, and make placement a separate explicit policy. Exercise asymmetric and sparse sysfs fixtures. [Cache discovery](/home/folk/Programs/brokkr/src/cpu_topology.rs:178), [CPU frequency and boost](/home/folk/Programs/brokkr/src/host/cpu.rs:37)
- **The topology input is effectively unbounded, and preparation has a separate CPU default.** CPU ranges expand directly into a `BTreeSet`, accepting partial malformed lists and allocating in proportion to the numeric interval. Cache and all-core probes also handle disjoint online and affinity observations differently. `prepare` independently spells the same `available_parallelism` fallback and `1..=8` clamp for its global reader permits and for worker count, so the two can observe different affinity or CPU state. Give CPU-list decoding a bounded range type and use a single captured work budget per operation. Test oversized ranges, hotplug inconsistencies, and changing probe answers. [List parser and online affinity](/home/folk/Programs/brokkr/src/cpu_topology.rs:77), [all-core discovery](/home/folk/Programs/brokkr/src/cpu_topology.rs:267), [preparation](/home/folk/Programs/brokkr/src/check_cmd/prepare.rs:1812)
- **Mount parsing has three owners.** The CPU quota reader understands escaped mount paths and non-root cgroup mount roots. The lock cgroup reader rejects both. A container can get the quota cap while cgroup containment is unavailable. Storage uses `/proc/mounts` and turns each UTF-8 byte into a separate Unicode scalar, corrupting non-ASCII mount points. It also accepts decimal digits in octal escapes. A failed match can associate a path's `statvfs` figures with the parent mount's label, after which deduplication can skip the real mount. Use one byte-preserving mountinfo decoder, with explicit containment eligibility, and fixtures for Unicode and non-UTF-8 names, escapes, bind mounts, and rooted cgroups. [Quota mounts](/home/folk/Programs/brokkr/src/cpu_topology/quota.rs:26), [lock mounts](/home/folk/Programs/brokkr/src/lock/cgroup.rs:279), [storage mounts](/home/folk/Programs/brokkr/src/host/storage.rs:93)
- **Storage identity, deduplication, and unknown space vary by caller.** `env` and health group on mount and device strings. The gate deduplicates on the mount string alone and rereads the mount table for each candidate. Storage inventory resolves `/dev` names and follows partition parents, while host trace independently starts at `st_dev` and follows a sysfs partition parent. A container that hides `/dev` or presents a mapped device can give different descriptions of the same storage. Failed `statvfs` becomes zero total, prompting an explicit unavailable row in `env` but a silent admission in the gate and a silent omission in `check`'s pressure report. Use a typed mount identity and probe result, and make admission on unknown an explicit decision with a diagnostic. Test failures of each underlying operation. [Storage probe](/home/folk/Programs/brokkr/src/host/storage.rs:30), [gate](/home/folk/Programs/brokkr/src/disk_gate.rs:59), [health](/home/folk/Programs/brokkr/src/health.rs:211), [trace device](/home/folk/Programs/brokkr/src/bench/host_trace.rs:39)
- **The capacity policies are hard to find and assume block space is the limiting resource.** The 5% admission and 10% state-pressure thresholds serve different purposes but each owns its own percentage comparison and stands in a different module. Neither checks free inodes, the write size, or a quota constraint hidden from the probe. The build gate deliberately excludes project state, which can still hold unbounded logs and caches. Keep distinct named thresholds on one disk policy, expose the effective values, and inject the probe and intended destinations. Use policy tests for both thresholds, unknowns, full inode tables, and writes on split mounts. Real headroom under concurrent writers will remain an observation. [Storage policy](/home/folk/Programs/brokkr/src/host/storage.rs:5), [state pressure](/home/folk/Programs/brokkr/src/health.rs:27), [gate rationale](/home/folk/Programs/brokkr/src/disk_gate.rs:1)

Host trace independently reads the same file and handles missing dirty/writeback values as `None`. Host-wide `MemAvailable` also says nothing about a tighter container memory ceiling. Clock ticks are queried again by the watchdog and historical sidecar rendering. A failed watchdog measurement records zero age, and historical formatting consults the current host for the divisor. The systemd trim stamp is a literal path whose absence silently removes the observation on other installations. Use typed boot, namespace, tick-rate, and uptime facts with explicit unknowns. ## Filesystem primitives and write ownership

- **Atomic replacement is a rename sequence, with ownership still supplied by caller convention.** `Staged::stable` takes a path and hands out a predictable sibling pathname. Its single-writer requirement is a comment. The module reopens the directory between initial write and publication, and drop removes a pathname rather than the inode it created. If the parent is replaced or the temp name changes, publication may fail and cleanup can act on a different file. The pre-rename identity check is separated from rename by permission changes and fsync. Retain the directory and staged-file capability through the transaction, require a lease for resumable stages, and test concurrent writers and directory replacement. [Staging contract](/home/folk/Programs/brokkr/src/atomic_write.rs:200), [publication and drop](/home/folk/Programs/brokkr/src/atomic_write.rs:315)
- **Replacement's symlink and metadata policies are implicit.** Ordinary replacement follows an existing symlink but changes the link itself if its target is missing. Durable replacement refuses a final symlink but durable directory creation trusts intermediate links. New temp files use `0666` less umask until publication copies permission bits. Owner, group, ACLs, and extended attributes have no carry-over contract, and failure to read the existing mode can silently leave default permissions. Linux directory-fsync support also changes the guarantee, with unsupported sync silent in the atomic tier. Make destination authority, temp permissions, metadata treatment, and required durability explicit in the API. Use filesystem fault tests and a private-by-default staging type. [Atomic and durable tiers](/home/folk/Programs/brokkr/src/atomic_write.rs:48), [directory chain](/home/folk/Programs/brokkr/src/atomic_write.rs:125), [mode and sync](/home/folk/Programs/brokkr/src/atomic_write.rs:350)
- **Single-file publication still has several implementations.** Bench cursor and serve state do direct temp writes and renames. Binary timings silently ignore temp-write failure and remove the temp only on rename failure. Launcher extraction and executable snapshots also hand-roll staging. Their owners should be the per-user bench and serve stores, the project accounting store, the launcher cache, and project artifacts respectively, all calling a publication primitive with the appropriate durability. A structural write rule can ban open-coded publication in those modules. Test partial writes, failed promotion, and a competing publication. [Cursor](/home/folk/Programs/brokkr/src/bench/host_trace.rs:237), [serve state](/home/folk/Programs/brokkr/src/serve/registry.rs:371), [timings](/home/folk/Programs/brokkr/src/check_cmd/binary_timings.rs:226), [launcher extraction](/home/folk/Programs/brokkr/src/launch/helper.rs:45), [snapshots](/home/folk/Programs/brokkr/src/runnables.rs:591)
- **Multi-file publication needs a different primitive.** Litehtml removes current reference metadata and then renames the PNG, JSON, and new metadata in turn. An intermediate failure leaves the old complete reference unavailable. Worktree lock seeding fsyncs the staged file but uses a separate rename path and leaves recovery to the next seed. Give the visual reference store immutable generations and a single published generation record. Let the provisioned worktree own its lockfile and staging transaction. Test a failure after each step. [Visual reference publication](/home/folk/Programs/brokkr/src/litehtml/reference.rs:125), [worktree lock seed](/home/folk/Programs/brokkr/src/worktree_lock.rs:121)
- **Project state is created even for read-only dispatch paths.** `ensure_self_ignored` runs before the read-only decision. It accepts an existing `.gitignore` of any contents and follows a symlinked state directory. A failed first write can leave a file that later invocations accept even though the ignore rule was never written. The reported error names `.brokkr/.gitignore` without the actual project or worktree. Separately, `env` calls dataset status and can populate the project hash cache, despite describing itself as touching nothing. Give mutating commands an initialized `ProjectState` capability, and let reports choose an explicitly read-only digest path. The project state owner should own cache writes and ignore-file policy. Test read-only dispatch without `.brokkr`, plus partial initialization and symlink cases. [Dispatch order](/home/folk/Programs/brokkr/src/main_parts/dispatch.rs:40), [state initializer](/home/folk/Programs/brokkr/src/clean/layout.rs:33), [env lock comment](/home/folk/Programs/brokkr/src/env.rs:89), [dataset status](/home/folk/Programs/brokkr/src/datasets/status.rs:173)
- **Several valid features write in another owner's tree.** Guard enrollment edits Cargo's user config. Toolchain disabling and config stripping temporarily move files in the source checkout. Install stamping later rewrites a Cargo-installed executable and puts scratch files beside it. Fixture lint seeds an ignored `Cargo.lock` in the source fixture. Prefer child-scoped Cargo configuration and a brokkr-owned build view, an isolated project-state copy of each fixture, and a brokkr-owned install stage. Cargo or the explicitly authorized installer should own the final install-directory promotion. Explicit guard enrollment, approval, and source fixes are genuine cross-owner operations and deserve their own narrow mutation capabilities. Check allowed write roots in integration fixtures. Textlint alone cannot certify subprocess writes. [Guard config selection](/home/folk/Programs/brokkr/src/guard.rs:72), [toolchain moves](/home/folk/Programs/brokkr/src/toolchain.rs:134), [Cargo config transaction](/home/folk/Programs/brokkr/src/cargo_config_strip/transaction.rs:1), [install stamp](/home/folk/Programs/brokkr/src/build_info.rs:219), [fixture seed](/home/folk/Programs/brokkr/src/check_cmd/fixture_lint/mod.rs:105)
- **The digest cache makes a correctness claim from host metadata.** Its two-second window is a hard-coded wall-clock test when *recording* an entry. The cache hit compares mtime, ctime, inode, and length, omitting device ID. Remounts, stale network metadata, and coarse or nonstandard timestamps can break the identity assumption. The stable reader checks type before opening through a different operation, and only checks inode identity after the read. A change to a special file in between can block the read. The uncached reader accepts any openable file and repeats the 64 KiB hash loop. Use one descriptor-based regular-file reader and define the filesystems or producer contracts on which metadata can stand in for content. Inject clock and stat results for tests. Filesystem coherence cannot be enforced by a Rust lint. - **Tree and cache codecs assume more about names than the filesystem does.** Tree hashing converts names lossily, so distinct byte names can produce the same relative name in the digest. It ignores empty subdirectories and crosses mount boundaries. Cache serialization excludes some names on write, silently drops bad records or read failures, and resolves pruning keys using `exists()`, which also returns false on errors. Use a versioned byte-path codec with explicit entry kinds and a stated mount policy. Test invalid UTF-8, case-only names, empty directories, unreadable cache entries, and a mount boundary. [Tree walk](/home/folk/Programs/brokkr/src/preflight/digest.rs:535), [cache codec](/home/folk/Programs/brokkr/src/preflight/digest.rs:710)
- **Cache and health walks have no enforceable resource envelope.** The hash cache loads and rewrites the whole file, holds a blocking flock over reread, existence scans and replacement, and only prunes on a save with updates. A growing set of still-existing files grows the cache indefinitely. The recursive tree walk also retains all entries for sorting. `health::usage` retains an inode set and a work stack, follows the root symlink, and cannot detect a same-device bind mount as an ownership boundary. Give cache storage its own entry and byte budget and bounded lock acquisition. Give each scan a depth, work and time budget with an incomplete result carrying the affected path. Test refusal under held locks and deliberately large inventories. [Hash cache save](/home/folk/Programs/brokkr/src/preflight/digest.rs:749), [health traversal](/home/folk/Programs/brokkr/src/health.rs:50)

## Output, diagnostics, and child supervision

- **Bounded forced output can still block the watchdog before killing anything.** `lock_patiently` bounds mutex acquisition at roughly 100 sleeps of 10 ms. After acquisition, the code does blocking file and stdio writes. The forced warning fallback takes the standard stderr lock, and the renderer takes the standard stdout lock even on some stderr-only paths. The watchdog calls forced output before initiating shutdown and again before its hard exit. Move liveness actions ahead of best-effort diagnostics and route emergency events through a bounded sink that drops or records loss without waiting on ordinary stdio. Test with unread pipes and a stalled sink, as well as a busy renderer. [Console locking](/home/folk/Programs/brokkr/src/output/console.rs:197), [forced fallback](/home/folk/Programs/brokkr/src/output/console.rs:530), [watchdog order](/home/folk/Programs/brokkr/src/check_cmd/watchdog.rs:275)
- **Console state and run-log state depend on call order.** Quiet, stream reservation, status enablement, renderer, log file, and log reservation live in separate globals. `RunLog` infers nesting from a process-global `Option`, without tying a borrower to the owner. Activation holds the reservation mutex across directory I/O, pruning, and diagnostics. Log writes precede renderer acquisition under a separate lock, so concurrent emissions can be ordered differently on disk and on screen. `detail_or_console` can observe an open log just before it closes. Make the session and stream ownership explicit and fan out a structured event carrying stable order and identifiers. Test overlap, nested lifetime, and log-open failure.
