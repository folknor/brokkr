# Lock and compile-capability hygiene report

This is a static review of acquisition, queueing, status, stop and kill, compile admission, and the process and filesystem boundaries they depend on. I read the relevant source, docs, and Git history. I changed no files and ran no builds, tests, or `brokkr` commands. Conditional failures below are deductions from the code.

I would rewrite the lock lifecycle around one host-local coordinator. Today the flock proves exclusion, the queue files decide admission, mutable file contents supply kill targets, and the socket owns cooperative stop. A coordinator could make an acquisition the unit of all four operations, use a monotonic clock for queue policy, and own a workload cgroup with the supervisor outside it. It should keep a stable kernel lock and an explicit compile-lease boundary. The findings below identify what that architecture would need to enforce.

## Host identity and filesystem ownership

- **One lock per `$HOME` spelling and mount view.** Holder and guard agree on unset and empty `HOME`. Both accept a relative value, which resolves against each process's own working directory. A holder and its Cargo child can consequently open different locks when the build runs in a worktree or a different directory. Different absolute homes or mounts also split exclusion. A shared home across machines can give them the same flock while their process IDs and socket endpoints belong to different kernels. Resolve a host-local lock domain once and hand it to child launches. Enforce an absolute, validated state root, and test differing child working directories and mount views. Documentation alone can describe unsupported filesystems, but cannot establish that two processes share an inode. [Path resolver](/home/folk/Programs/brokkr/src/user_dirs/paths.rs:13) · [Lock acquisition path](/home/folk/Programs/brokkr/src/lock/mod.rs:432) · [Guard path resolution](/home/folk/Programs/brokkr/src/bin/rustc_guard.rs:488)
- **Paths are treated as proof of ownership.** The global and compile lock opens follow symlinks and lack a regular-file or owner check. Their liveness and exclusion depend on the inodes staying put. An external deletion or replacement splits the lock, and a symlink can direct lock-record writes and truncation outside brokkr state. Queue and socket operations also resolve through directory paths, including a socket directory that the code chmods. Brokkr should own a private state-directory descriptor and use validated, descriptor-relative opens for stable files and cleanup. A dependency rule can reserve raw mutations of this state for its owner. Integration tests can enforce the regular-file, link and inode invariants. [Lock opens](/home/folk/Programs/brokkr/src/lock/mod.rs:850) · [Guard lease open](/home/folk/Programs/brokkr/src/bin/rustc_guard.rs:224) · [Socket directory](/home/folk/Programs/brokkr/src/lock/service.rs:115) · [Queue filesystem operations](/home/folk/Programs/brokkr/src/lock/queue.rs:239)
- **Inspection has write authority.** `status()` creates the state directory and opens the lock with `O_CREAT | O_RDWR` after an `exists()` check. The probe can recreate a vanished lock, requires write access to inspect an existing lock, and treats some metadata errors as absence. The socket client creates and chmods the socket directory through the server's helper. Whole-command `lock`, `kill` and `guard` also take bootstrap's ordinary history-write path. Give observation read-only opens and a lookup-only socket path. If these commands should record history, name the separate write to brokkr's user history database in the contract. Enforce the observation boundary with a read-only filesystem test. - **The queue root has two owners.** `user_dirs::queue_dir_at` constructs the path used by inspection and cancellation. `queue_dir_for` independently appends `"queue"` beside the file used for acquisition. They agree for the current global layout. The latter also gives any two lock files in one directory a shared admission index. Construct the lock, queue, compile lock and socket directory from one layout value, with distinct lock identities where multiple locks are supported. A layout API and an integration test can enforce this. [Inspection layout](/home/folk/Programs/brokkr/src/user_dirs.rs:24) · [Acquisition layout](/home/folk/Programs/brokkr/src/lock/mod.rs:464)
- **Socket reachability is a host prerequisite.** A filesystem Unix socket under `$HOME/.brokkr/lock/<id>.sock` makes a long home path, a filesystem without socket support, or unavailable bind permissions fatal to acquisition. ## Acquisition, queue and cancellation

- **Same-process re-entry has a race before registration.** `HELD` is checked early and populated after service startup, drain, authorization and cgroup entry. A second thread can miss the first, open another descriptor, and keep polling for a flock that this process already owns. The loop never rejoins `HELD`. A later thread can re-enter and start work once registration occurs, while the fresh holder is still running post-acquisition hooks and before dispatch consumes maintenance. `take_maintenance` is one-shot, but any re-entered guard could take it first. Give the acquisition owner a structural `Pending`/`Ready` transition and give re-entry an explicit borrow of an initialized hold. Test simultaneous entry and maintenance ownership with barriers. [Registry check](/home/folk/Programs/brokkr/src/lock/hold_protocol.rs:204) · [Registration and hooks](/home/folk/Programs/brokkr/src/lock/hold_protocol.rs:489) · [Maintenance token](/home/folk/Programs/brokkr/src/lock/mod.rs:299) · [Dispatch](/home/folk/Programs/brokkr/src/main_parts/dispatch.rs:102)
- **Ambient hold lookup selects by two different rules.** Work, cgroup escape and tree recovery re-resolve a path and match it. Capability and activity lookups select the first registry entry with the respective field. One production path normally hides the divergence. Multiple holds, path aliases or a changed root can leave the APIs talking about different locks. Even a lookup for watchdog recovery calls `lock_path()`, which can create directories and block before the recovery thread's five-second wait starts. Pass an acquisition-bound context to spawn and recovery, and hand recovery a snapshot before entering its bounded operation. A type can prevent combining another hold's capability, workload and cleanup authority. [Hold lookup APIs](/home/folk/Programs/brokkr/src/lock/mod.rs:623) · [Watchdog tree restoration](/home/folk/Programs/brokkr/src/tree_policy.rs:102)
- **The queue's arrival timestamp, publication order and admission order differ.** The record becomes visible to `kill` before the waiter has an admission ticket. A later waiter, or a nonblocking acquisition, can get `admit.lock` first and pass a published waiter with no ticket. The reference defines arrival as ticket creation, while the command docs say join order. A cancelled or failing ticket can also leave an index entry until another admission settles it. A stopped process or stalled filesystem operation under `admit.lock` blocks everyone, including readers that need a new position. The mutex covers directory scans, metadata, file opens, flock attempts and ticket creation/deletion. One queue transaction or coordinator should own visibility and order, with an interleaving test for publish, admit, cancel and claim. ## Holder records, socket and stop

- **The file and socket publish different snapshots.** A failed live metadata write clears the mutable file fields if recovery succeeds, while `LockInner::publish` still sends the original snapshot to the socket. Matching reads prove stability between reads, and a writer paused mid-write can still yield the same partial record twice. `LockState` is held over process checks, file writes, socket snapshot publication and possible warning output. Use the stable flock inode for exclusion and publish a bounded, atomic, acquisition-tagged snapshot elsewhere. Let the supervisor own child registrations and surface publication degradation. Enforce transaction boundaries structurally and exercise short writes and partial recovery with faults. ## Process ownership and cleanup

- **Process identity and acquisition identity are separate, and numeric kill checks only the former.** A pidfd pins a process generation. It cannot prove that process still owns the acquisition whose scope was read. A still-running holder can release between scope lookup and numeric SIGTERM or SIGSTOP. Hard kill also resumes descendant selection from a bare root PID after preflight, so a changed root can lead to a different tree even though the final holder signal uses the old pidfd. Make termination an acquisition-scoped operation on a control endpoint or workload handle. Model a release/reacquire during preflight in a test. The preflight identity sandwich remains useful for individual targets. [Graceful fallback](/home/folk/Programs/brokkr/src/lock_cmd.rs:628) · [Hard-kill sequence](/home/folk/Programs/brokkr/src/lock_cmd.rs:720) · [Bare-root descendant walk](/home/folk/Programs/brokkr/src/shutdown.rs:726)
- **The group-signal policy has diverged from the test supervisor.** Lock kill rechecks a recorded group leader, then uses numeric `kill(-pgid)`, with a documented reuse race. The test supervisor already uses the kernel's pidfd group signal where supported and a fallback whose safety rests on owning the unreaped child. External `kill` lacks that fallback proof. Share group capability detection and typed signal outcomes. On hosts where the group API is unavailable, a verified member walk or a delegated workload cgroup can carry the weaker or stronger guarantee explicitly. Test support, absence, permission failure and leader exit separately. [Lock group signaling](/home/folk/Programs/brokkr/src/lock_cmd.rs:1142) · [Test supervisor group signaling](/home/folk/Programs/brokkr/src/test_runner/leader.rs:1)
- **Kill and reap can lose the failures an operator needs.** `kill_descendants` returns a count and drops scan, verification and delivery failures. The leaderless sweep discards unreadable env, pidfd-open and rescan failures. `PidfdRefusal::OpenFailed` drops errno, conflating a vanished process with blocked syscalls, descriptor exhaustion or a missing kernel feature.
