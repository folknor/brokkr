# Hygiene report: results server and stores

The results server and the bench client already share most of the write protocol. Ownership breaks down around that core: three clients interpret server identity differently, three stores implement overlapping SQLite lifecycle rules, and sidecar queries interpret the same evidence differently depending on where it came from. Some of those differences already produce incorrect results, including a typed run displaying another run’s samples, a query describing an old sample span as the selected run’s wall, and a documented dry run that can migrate both databases.

This is a static review of the repository and the relevant producer code in sibling checkouts. Runtime consequences below are inferred from the cited code. I made no workspace changes.

## Enforcement that already exists

- **The bench wire and migration chain have real owners.** The server compiles the same store source by path. The route, protocol header, protocol version, request cap and connection deadline are shared, and the client’s ordinary attempt timeout derives from that deadline. Frozen protocol fingerprints, decode fixtures and migration checksums catch different kinds of drift. The store’s sample shape is also checked against the sidecar and the resulting SQL columns. Those checks are worth keeping through an internal rewrite. [Wire contract](/home/folk/Programs/brokkr/reference/bench-store.md:685), [Migration chain](/home/folk/Programs/brokkr/reference/bench-store.md:865), [Server crate boundary](/home/folk/Programs/brokkr/src/bin/results_server/main.rs:18)
- **The convention gates provide several enforcement levels.** Gremlins covers source characters, textlint covers paths, fixed spellings and import seams, script checks can run a behavioral probe, dependency rules inspect direct package dependencies, and fixture lints prove that a configured Clippy ban still fires. This repo already checks the bench-store import boundary, selected state paths, selected reservation mutations and operator prefixes. Those text rules have explicit scopes. For example, the reservation rule does not cover sidecar namespace code, and the operator rule catches a list of bracketed prefixes rather than every way to write narration. Cargo denies raw print macros with function-level exceptions for data. - **There are useful injection and ownership precedents in scope.** `Limits` is injectable into the HTTP layer, server race tests use paused Tokio time, client tests supply retry policies, the sidecar supplies a `SidecarSampler`, and the XDG resolver has a pure input-based test seam. The worker moves one SQLite connection onto one thread. `Timeline` owns marker ordering and phase lookup, and `define_sample!` owns the typed sample’s aliases, fields and column projection. The findings below identify where those boundaries stop. ## Server identity, configuration and host assumptions

- **The endpoint has two definitions.** `wire::PATH` owns `/bench` at the server, but `ResultsServer::parse` appends a literal `/bench`. Deploy takes the full route in TOML and appends a literal `?probe=`, whose name is also spelled in the server’s query parser. The deployment example repeats the backend port in `ExecStart`, the proxy target and the deploy declaration, and the public port in the proxy and client configuration. Changing one can leave a healthy server that the client or deploy cannot find. Enforce the programmatic spellings with a shared endpoint type, and render or exercise the host wiring from one deployment declaration. The public and backend addresses represent different roles and can retain different values. [Wire constants](/home/folk/Programs/brokkr/src/bench/store/wire.rs:23), [Client endpoint](/home/folk/Programs/brokkr/src/config_parts/user.rs:79), [Probe parser](/home/folk/Programs/brokkr/src/bin/results_server/identity.rs:60), [Deployment example](/home/folk/Programs/brokkr/docs/results-server.md:100)
- **The URL validators already disagree.** The main client refuses credentials and invalid explicit ports during configuration composition. Deploy independently checks scheme, host, query and fragment, with no equivalent credential or explicit-port check and no check that the URL names the identity route. A wrong route is discovered after the restart command ran. Both validators put the original URL into errors, including the main client’s credential refusal. Use one parsed URL type with explicit base-URL and identity-endpoint constructors, safe display, and tests that fail before invoking the restart program. [Client URL parser](/home/folk/Programs/brokkr/src/config_parts/user.rs:79), [Deploy checks and order](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:149)
- **Three readers define what counts as the same server.** Bench startup accepts JSON with the expected `protocol` alone. The version banner accepts any JSON, treats fields individually as optional, and can print it as an unstamped server. Deploy requires `server`, protocol, nonce and a 32-character ASCII hexadecimal build. The emitter always writes lowercase and deploy’s validator also accepts uppercase, which then fails the case-sensitive comparison. Deploy sends no protocol header, although the wire reference says every request sends one. The current GET server ignores that header, so this survives today. Use one identity codec and explicit policies for compatibility reporting, preflight and deployment proof. Exercise all three against the same reply fixtures. - **The build identity crosses binaries, and `.brokkr.build_info` really is duplicated.** The installer and server independently name the ELF section. The reader is already shared by path, so the binary boundary permits sharing the name too. The server name is also repeated in the Cargo target, Clap metadata, install/version discovery and two output renderers. The ELF reader and the server digest each name `/proc/self/exe`; the digest also reimplements the same xxh3-128 streaming loop and 64 KiB buffer used by preflight. - **Stamp loading happens on first GET.** The stamp is resolved through a process-wide `OnceLock` that performs synchronous file I/O on a Tokio thread. ## Admission, retry, ownership and growth

- **`Limits` is useful but incomplete as an inventory.** It contains 256 connections, 64 in-flight requests, 64 queued jobs, 1 GiB admitted request bytes, 256 MiB per request, and 10/120/60/300-second phase and connection bounds. The 64 KiB header buffer, 1 KiB reservation unit, 100 ms accept retry, SQLite’s 5-second busy wait, and host-sized Tokio worker pool live elsewhere. The accept loop retries every error forever and logs each failure. The phase assertion checks whole seconds on the compiled default only, and leaves response egress in the remaining connection time. Give serve one validated policy and effective-settings view. Test relationships among byte limits, semaphore capacity, phase budgets and egress, and classify accept failures independently of retry timing. [Server limits and runtime](/home/folk/Programs/brokkr/src/bin/results_server/main.rs:77), [HTTP admission and accept](/home/folk/Programs/brokkr/src/bin/results_server/http.rs:33), [SQLite timeout](/home/folk/Programs/brokkr/src/bench/store/schema.rs:398)
- **Deploy and ordinary retries implement separate clocks and backoff loops.** Deploy has a 300-second default, 10-second probes, 100 ms to 2 s backoff, 50 ms restart polling and a one-second watchdog grace. The normal client uses a 10-second connect and 330-second attempt, a separate 3/10-second version probe, read and publication policies with 250 ms backoff, and another stop polling loop. The ordinary read window is 20 seconds but one attempt can take 330 seconds. Those policies serve different operations; their start, cancellation, retry admission and time-source semantics should share primitives. Existing client policy injection changes retry windows and sleeps, while deploy tests still need real sleeps and processes. Inject a clock and sleeper and test boundary instants. [Deploy constants](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:26), [Deploy retry](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:256), [Client timeouts](/home/folk/Programs/brokkr/src/bench/remote.rs:19), [Retry admission](/home/folk/Programs/brokkr/src/bench/publication.rs:17), [Deploy tests](/home/folk/Programs/brokkr/src/bin/results_server/deploy_tests.rs:128)
- **The deploy watchdog has uncovered work and ambiguous outcomes.** Declaration reading is before its deadline and uses an unbounded `read_to_string`; a FIFO at the config path can block the caller before the watchdog exists. `recv_timeout` maps a disconnected worker and an elapsed deadline to the same timeout message. `stop` discards wait and kill errors and can report “killed” after a failed reap. [Deploy watchdog and load](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:82), [Restart termination](/home/folk/Programs/brokkr/src/bin/results_server/deploy.rs:201)
- **Write certainty depends on transport assumptions the application never sees.** The remote client infers non-delivery from selected ureq error types and Linux TCP behavior, and assumes a bare intermediary 4xx arrived before application. Its agent retains normal proxy resolution; deploy opts out. The client accepts a publication’s HTTP 200 as an acknowledgement even when the body is unreadable, and does not check the response protocol header. This is documented policy, with the consequence that a misconfigured intermediary returning its own successful response can falsely settle a write. A versioned acknowledgement tied to the submitted UUID, explicit proxy policy and conservative certainty where delivery cannot be proved would move this invariant into the protocol. Some exceptions are meaningful, such as 404, 405 and 411 for `bad_request`. Adding a kind can leave it treated as an unknown tolerant envelope unless the manual inverse list is updated. ## SQLite and the typed history readers

- **SQLite lifecycle rules already disagree.** Typed stores and the bench store each own a five-second busy timeout, foreign-key setup, WAL, schema stamps, migration transactions and rollback. The bench store verifies WAL, refuses negative versions and tests for an unstamped foreign schema. The typed helper just asks for WAL and accepts any version below its maximum. Neither stamps an application identity. A foreign database with a plausible nonzero `user_version` can pass the version check, potentially receive migration/DDL, and fail later with missing tables. Results even has an explicit historical exception for litehtml’s reused stamp. Share connection and migration machinery, give each store an application identity, and confine bespoke shape recognition to legacy import. Verify foreign-file refusal before mutation with database fixtures. ## Architectural conclusion

I would rewrite the storage and query boundaries. Give current results one catalogue with bounded, revisioned operations and a validated remote representation. Put the two historical typed schemas behind a read/import adapter with independent old-file fixtures. Give the server an owned database directory and a worker that owns the connection, lock and job lifecycle together. At the process boundary, resolve host capabilities, layout, clock, limits and output once and hand them to the code that uses them.

That design removes the mechanisms behind the concrete failures in this report. A run index can be validated before it reaches SQL. A query cannot acquire write access by opening a history file. A remote answer cannot become evidence before its identity and references are checked. The existing checks for frozen wire bytes, migration steps and sample columns provide a practical way to hold those properties across the standalone binary and producer boundaries.
