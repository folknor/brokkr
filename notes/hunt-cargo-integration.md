# Cargo integration hygiene report

I read the Cargo integration code, its callers in build, launch, check, cleanup and guard, and the relevant documentation. The findings below come from source inspection. I made no filesystem changes and ran no builds, tests or `brokkr` commands.

I would rewrite this integration around a typed Cargo invocation. Resolve the executable, physical working directory, environment, arguments and toolchain once per invocation. Carry that same value into preflight, execution, provenance and diagnostics. Give artifact storage its own ownership model and decode Cargo's message stream once for all consumers. The existing splits let two parts of brokkr make different decisions about the same child, even when both use shared helpers.

## Existing enforcement

The repo already has the right mechanisms for much of this work. Gremlins and textlint catch textual drift, including copied state paths and probe literals. `must_scan` and `require_live_paths` can keep a rule from quietly losing coverage. Script checks and fixture lints can prove behavior against a real subprocess. Dependency rules and compiler visibility can keep walk-up config discovery, process spawning and artifact mutation behind their owners. The existing rustc probe lint catches `-vV` spelled outside the owning module, but allows several distinct probe implementations inside it. The output lints cover direct printing and handwritten prefixes. They leave room for differences in severity, provenance, duration formatting and data exposure. ## Cargo configuration and environment

- **Cargo home has two resolvers.** `user_dirs::cargo_home` serves guard enrollment and part of crit provenance. `rustflags::cargo_home` serves Cargo launch reconstruction and install. Both spell the `CARGO_HOME` → `HOME/.cargo` → passwd fallback and ignore empty inputs. The user-dir version anchors relative `CARGO_HOME` to the current process and can return a relative path through `HOME`. The launch version anchors both to the supplied child directory. Using different directories for different operations is legitimate. Duplicating the rule makes each caller responsible for keeping that distinction correct. **Enforcement:** one pure resolver taking a physical cwd, an environment view and an account-home lookup. Allow reads of those variables only at the boundary. [user_dirs.rs](/home/folk/Programs/brokkr/src/user_dirs.rs:144) · [rustflags.rs](/home/folk/Programs/brokkr/src/rustflags.rs:527)

- **There are three views of config selection.** Cargo launch reconstruction walks ancestors, home and includes. Guard enrollment edits one selected home file. `[cargo_env]` adds its own parser for `--config` arguments. The two config basenames are also spelled independently in discovery, strip recovery and guard's write checks. A concrete consequence is that install root discovery knows Cargo reloads config from the `install --path` package, while the environment conflict check starts from the launch cwd. A package-local `[env]` can escape brokkr's conflict check for the install that consumes it. **Enforcement:** one invocation descriptor carrying both config search roots when the command requires them, one basename definition, and a fixture for `install --path` with a package-local override. - **The config reader has an implicit Cargo version floor.** It follows 1.97's include normalization and 1.98's `[env] relative` provenance. The comments identify concrete divergence from earlier Cargo versions. A symlink followed by `..` in an include can select a different file, and a higher layer supplying only `force` can change which directory Cargo uses for a relative value. Target preflight's only Cargo floor is 1.89, for doctests. **Enforcement:** make compatibility a property of the selected Cargo, checked when a feature needs it. Use a supported-version fixture matrix or delegate the resolution to Cargo. [rustflags.rs](/home/folk/Programs/brokkr/src/rustflags.rs:480) · [rustflags.rs](/home/folk/Programs/brokkr/src/rustflags.rs:854) · [target_platform.rs](/home/folk/Programs/brokkr/src/target_platform.rs:557)

- **Config lookup blurs absence, unreadability and blocking I/O.** The legacy probe opens `config` before strip or guard can reject a non-regular object. A FIFO can block the brokkr thread before there is a supervised child. Modern config selection and optional includes use `.exists()`, which erases inspection errors. The include reader has no limit on total bytes, document count or recursion depth. Its set catches repeated path spellings within one root, while a deep chain of distinct names still consumes stack and memory. **Enforcement:** a bounded discovery interface with typed inspection failures, explicit file-kind policy and fixtures for a FIFO, unreadable include and deep chain. Cargo parity at this boundary should include the refusal reason and the supported host behavior. - **`CARGO_BUILD_TARGET` has more than one resolution rule.** Launch checks treat even an empty variable as an ambient target setting. Rustflags placement parses it as a comma-separated string and falls back to file or host when it gets no usable entries. The `--no-build` implementation explicitly documents Cargo's whitespace splitting, merging with config arrays and canonicalized JSON-target stems. Rustflags placement takes a lexical file stem. An empty value, a multi-target value or a symlinked target spec can change the selected rustflags layer. **Enforcement:** one target value with explicit absent, configured, invalid and unresolved states. Callers can make different policy decisions from that same value. Test empty values, arrays, explicit `--target`, `host-tuple` and symlinked specs against Cargo. - **The rustflags resolver, injector and explanation can disagree.** `effective_rustflags` reconstructs tokens, `triple_source_live` independently decides whether a layer wins, and `compose` independently encodes the environment. An unknown matching table can make reconstruction give up while the placement machinery can prove that the target layer is live. Those are distinct facts worth representing explicitly. There is also an ordering problem. - **Rustc argument grammar is repeated for three jobs.** Cfg extraction keeps an operand-taking list, stripping groups `-C` and `-Z` and maintains operand-less lists, and the guard has its own conservative probe classifier. The policies have different purposes. Their common dependency is where an option ends and its operand starts. String rewrites also re-tokenize the entire edited string with Rust's `split_whitespace()` and single-space joining. **Enforcement:** share an argument grammar where the boundary permits it, keep each policy explicit, and use an argv corpus for split and attached operands, `--`, response files and token boundaries across layers. - **Cargo `[env]` has two applicators and several snapshots.** `CargoProbe` and `DirectRuntime` independently implement forced values and hole filling. The former updates a retained full environment or an overlay. The latter builds an overlay and rereads inherited `LD_LIBRARY_PATH` when constructing each binary's envelope. The latter also says that Cargo-owned values are applied last, then appends build-script variables that can overwrite some of those keys. - **Non-UTF-8 survives some paths and changes meaning in others.** The launch receipt and frozen environment preserve Unix bytes. Compiler and wrapper selection discard non-UTF-8 environment values and try lower-priority inputs. Relative config values and several target, install and manifest paths use `display().to_string()` or lossy conversion before they become child arguments. A checkout path containing non-UTF-8 can therefore be preserved in a receipt yet point somewhere else during a probe or path override. **Enforcement:** use `OsStr`, `OsString` and typed paths through command construction. ## Compiler, target and subprocess identity

- **Three compiler queries describe different compilers.** The plain cached `rustc -vV` runs `rustc` from the project directory. Target templates, target cfg and libdir use the selected `RUSTC`/`build.rustc` but skip wrappers and Cargo config `[env]`. Launch preflight uses `CargoProbe` with both wrapper levels and `[env]`. A wrapper that changes the reported host or sysroot is visible to one path and invisible to another. That affects `{host_arch}`, matching runner and rustflags tables, direct test loader paths, the deps host graph and crit's compiler stamp. `target_platform.rs`'s module-level claim about every probe therefore overstates the implementation. **Enforcement:** make these operations consume the selected compiler command and environment as a value, with a separately named query for ambient rustc when that is genuinely the question. Add a wrapper fixture that changes the answer. [cargo/rustc.rs](/home/folk/Programs/brokkr/src/cargo/rustc.rs:21) · [target_platform.rs](/home/folk/Programs/brokkr/src/target_platform.rs:163) · [target_platform.rs](/home/folk/Programs/brokkr/src/target_platform.rs:246) · [crit_cmd/stamp.rs](/home/folk/Programs/brokkr/src/crit_cmd/stamp.rs:56)

- **Host cfg combines facts from two machines.** `Platform::Host` takes OS, architecture, family, endian and pointer width from the brokkr executable and guesses vendor and environment from the probed triple's fields. `TargetFacts::host` can instead read the configured compiler's cfg, including features. A compiler running under emulation or reporting another host can produce a hybrid answer in the former path. `CargoLaunchConfig` can use that answer to rule out a runner, while launch preflight can find the runner using the compiler's facts. The deps projection also calls the approximation a `--filter-platform` view even though it retains unknown selectors. **Enforcement:** typed compiler facts or a Cargo-derived projection. Keep uncertainty in the domain model and test a deliberately different compiler host. The existing choice to let actual execution decide binfmt compatibility should survive the rewrite. [rustflags.rs](/home/folk/Programs/brokkr/src/rustflags.rs:1740) · [rustflags.rs](/home/folk/Programs/brokkr/src/rustflags.rs:1859) · [target_platform.rs](/home/folk/Programs/brokkr/src/target_platform.rs:269) · [cargo/metadata.rs](/home/folk/Programs/brokkr/src/cargo/metadata.rs:768)

- **Cross-target readiness assumes a sysroot layout.** `SweepTarget::resolve` checks `$sysroot/lib/rustlib/<triple>/lib`, then separately asks the compiler for `target-libdir`. A valid nonstandard layout can fail the first check, and an empty directory passes it. `is_dir()` also turns an inspection fault into an instruction to install the target. The Cargo version parser accepts only major `1` and assumes the second whitespace-delimited token is its version. **Enforcement:** use the selected compiler's reported libdir and a typed readiness check. - **Version parsing and error handling have drifted inside the probe owner.** There are three constructions of `-vV`. Rustc and target probes flatten unsuccessful completions into `Build` text, losing the typed ending that the child runner already exposes. The rustc wrapper path prints the outer program plus `-vV` and omits the actual chain and cwd. `RustcInfo` accepts empty or repeated `host:` and `release:` fields. `TargetCfg` accepts any nonempty line as a flag or key/value and can treat a wrapper banner or empty successful output as platform facts. **Enforcement:** one argv constructor, typed exit propagation, and strict protocol decoders that distinguish an incomplete probe from a genuinely absent cfg. - **The caches block unrelated work and key only part of the context.** Metadata and both rustc caches hold their map mutex through spawning, waiting and parsing. A slow probe under one key holds up every other key in that map. The keys include paths and, for some probes, explicit env pairs. Metadata enumerates `DevError` variants, while rustc turns unfamiliar variants into `Build` and both recreate I/O errors from kind and text. **Enforcement:** invocation-owned caches keyed by immutable inputs, with per-key coordination, a retention limit and shared typed errors. - **Provenance can omit the very input that changed.** Crit reads both raw rustflag variables, silently omits a failed compiler probe, and has a separate config digest walk. ## Cargo records, failures and operator output

- **A completed Cargo stream means three different things.** Test binary discovery accepts any JSON record with reason `build-finished`, regardless of `success`. Nextest searches for a literal substring, so a non-record can satisfy the check and a spacing change can defeat it. The serial gate requires a boolean and uses it. Binary discovery then silently drops malformed artifact records, so even a real terminal record can certify an incomplete inventory. The serial verifier also accumulates `String` data until the terminal record with no bound in that accumulator. The general capture caps do not establish a bound on this separate state. **Enforcement:** one streaming decoder with typed events and a completion state. Require validated records where an inventory serves as evidence. Test contradictory, malformed, missing and oversized streams against every consumer. [binaries.rs](/home/folk/Programs/brokkr/src/check_cmd/binaries.rs:269) · [nextest_lane.rs](/home/folk/Programs/brokkr/src/check_cmd/nextest_lane.rs:1092) · [test_execution.rs](/home/folk/Programs/brokkr/src/check_cmd/test_execution.rs:569)

- **The diagnostic JSON parser guesses ownership from serialization.** A malformed line gets flagged only if it starts with exact `{"reason":` after leading whitespace. A different key order or spacing can make the same malformed Cargo record disappear. A parseable record with a missing or non-string `reason` is also dropped, because test output shares the channel. The malformed-record error can attach the entire line, including a long source excerpt, absolute paths, or data from a build script. Unknown severities go to detail, as the output contract specifies, but carry only the stdout line number. On a shared log that leaves the sweep, command and package unidentified. **Enforcement:** attach invocation provenance to parse events, bound and redact raw excerpts, and apply strict framing while Cargo owns the stream. Preserve upstream extensions as typed observations so each consumer can handle them consistently.
