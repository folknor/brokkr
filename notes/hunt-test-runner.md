# Test-runner hygiene review

This is a read-only source review of the test runner, focused `test` command, test-code classifier, orphan reaper, and fixture scratch allocator. I followed their boundaries into check orchestration, Cargo configuration, process supervision, accounting, and cleanup. The behavior below is established by tracing the code and comparing it with the manuals. Host failure scenarios are conditional.

I would rewrite the execution core around one run-owned supervisor. It should own the resolved toolchain and launch environment, the child and its process identity, absolute deadlines, bounded streams, and a typed execution record. `test`, `check`, the Cargo shim, and the nextest adapter can still select and schedule work differently. Their results should come from the same evidence rules. The present split already lets serial `check` accept an incomplete stream and focused `test` accept the right count of the wrong names.

## Launch configuration and host resolution

- **Cargo home has two resolvers.** Both try a nonempty `CARGO_HOME`, then `.cargo` below a nonempty `HOME`, then the passwd home. The user-dir helper anchors relative `CARGO_HOME` to the process cwd and returns a relative `HOME` fallback as spelled. The launch resolver anchors both to Cargo's supplied cwd, normally the physical build root, and returns a typed failure when neither source yields a home. Relative settings can therefore identify different Cargo config trees when the invocation directory differs from the build root. Explicit target sweeps and forwarded `--target` add more branches, and the runner's own argv scan takes the first match. ## Output, accounting, and growth

- **Focused test streams bypass the output channel.** The live forwarders and repeat-buffer flush write directly to stdout and stderr.
