# Config, CLI, and startup hygiene report

The largest ownership problem is that brokkr has a command catalogue, a config loader, and typed checkout roots, but none of them produces the complete invocation that actually runs. Dispatch and handlers rediscover roots, reinterpret flags, and acquire or activate resources independently. The same split appears in configuration: brokkr validates a composed TOML tree, then reconstructs parts of it for profile resolution, script benches, and operator reports. Several copies already disagree.

I would rewrite this around two objects: a compiled configuration with source locations and a resolved command request with explicit effects. Keep the existing TOML grammar, precedence, aliases, defaults, and stored-data readers at the boundaries. Give the request the roots, environment, host facts, deadlines, output streams, and capabilities it needs. A separate operation can revalidate inputs that genuinely must be sampled later, such as a checkout's identity after a lock wait.

This was a static inspection. I made no file changes and ran no builds, tests, or `brokkr` commands. The proposed checks below are enforcement options. Claims about unused code are based on repository references, so they do not establish what external scripts or sibling projects use.

## Existing enforcement and where it stops

- **The repo already has several of the right mechanisms.** Gremlins enforce text hygiene. Textlint can distinguish Rust code, strings, comments, and test code, with `must_scan` and `require_live_paths` to catch lost coverage. Script checks handle rules that need semantic inspection, including the guard decision probe. Dependency rules check workspace edges. Fixture lints check that a forbidden API actually fires its Clippy lint under the intended config. The repo uses these mechanisms to protect the Dellingr seam, bench-store independence, state-path construction, and console prefixes. The CLI tests cross-check command names in both directions. The config reference test cross-checks `SECTIONS`, with no equivalent check for `VALUE_KEYS`, user-layer keys, merge exceptions, or consumers. ## Errors, diagnostics, and data boundaries

- **OS strings can abort the process before a refusal is possible.** Public startup collects `std::env::args()` twice, even for path and passthrough arguments. On Unix a non-UTF-8 argument panics before Clap. `captured_env_map` uses `std::env::vars()`, which can panic on an unrelated non-UTF-8 entry before the name filter runs.
