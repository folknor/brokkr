# Launch and install hygiene report

I traced `run`, `build`, `install`, `passthrough`, and `--version` through their normal entry points, including the launch helper and the handoffs to Cargo, serve, and script benches. The findings are from source and documentation. I ran no builds, tests, or `brokkr` commands.

The architecture warrants a rewrite. Give each invocation a typed build and launch context that owns the selected Cargo unit, effective environment, directories, capabilities, and deadlines. Keep Cargo responsible for computing the launch environment and the static helper responsible for the final handoff. For install, give the destination backend one transaction that owns publication and provenance. Today the strongest transaction in the install command protects a post-install copy, while the delivered executable and its stamp are published separately.

Textlint can restrict spellings to an owner, distinguish Rust code from strings and comments, and check that rules actually reach named files. Script checks can verify relationships across files and exercise real subprocess boundaries. Manifest and dependency rules can constrain crate edges. Fixture lints exercise the policy in consumer-shaped workspaces. The repository already applies these ideas to `.brokkr` layouts, `rustc -vV`, the Lua and bench-store boundaries, reserved-path mutations, and console framing. The current reserved-mutation rule covers `atomic_write` and bench code, so it does not establish launch or install write ownership. ## Cargo inputs and executable identity

- **Worktree isolation already differs by command.** Plain `run --commit` sets both `CARGO_TARGET_DIR` and `CARGO_BUILD_BUILD_DIR`. Ordinary `build --commit`, `run --with`, serve, and bench worktree builds through `BuildRecipe` set only `CARGO_TARGET_DIR`, unless a bench rustflags recipe supplies both. An absolute inherited or configured build directory therefore remains shared on those paths. Metadata and no-build lookup have another target-only override, and runnable discovery passes no override. This is a difference in the effective Cargo inputs for the same worktree. **Enforcement:** an isolated-build directory pair in the recipe, used by discovery, build, probe, and launch. Test it with a conflicting inherited build directory. [Plain run](/home/folk/Programs/brokkr/src/runnables.rs:279) · [Build recipe](/home/folk/Programs/brokkr/src/build.rs:602) · [Metadata override](/home/folk/Programs/brokkr/src/build.rs:344) · [Runnable discovery](/home/folk/Programs/brokkr/src/runnables.rs:89)
- **The two Cargo invocations in plain `run` share argv selection and evaluate build inputs separately.** Captured build and quiet run both evaluate `[cargo_env]`. Probed build and probe evaluate it once and reuse the map. A generator whose answer changes can make the quiet run rebuild, include that rebuild in the reported runtime, and launch a different artifact from the captured build. The docs permit re-evaluation and rebuilds on this path. The design note's claim of one `BuildRecipe` across the launch forms overstates the implementation. **Enforcement:** an explicit recipe contract for when re-evaluation is permitted, with a fixture whose generator returns a different value on its second call. - **Plain `run` validates its runner after the captured build.** The preflight sees the caller's environment pairs, while the later Cargo spawn evaluates `[cargo_env]` and applies child policy. The probed path preflights the frozen map before its build. A blocked `--commit` or a failed host probe can also be discovered only after compilation. **Enforcement:** freeze each leg's real inputs before preflight and require a successful preflight value at spawn. The launch model anchors either relative value at Cargo's explicit cwd. `user_dirs::cargo_home`, used by guard enrollment, anchors relative `CARGO_HOME` at the current process cwd and leaves a relative `HOME` fallback relative. Install root detection calls the launch resolver with the supplied build root and walks package and build paths directly, while ordinary launch discovery first canonicalizes the cwd. Relative or symlinked layouts can therefore select different config locations. Brokkr's own state intentionally has a different rule, accepting nonempty `HOME` with no account fallback or absolute-path check. A relative `HOME` can split the supposedly per-user lock and state across invocation directories. **Enforcement:** one pure Cargo-home resolver over an explicit OS environment and physical cwd, plus a separately named validated brokkr-state root. ## Launch helper, environment, and process ownership

- **The helper's separate compilation requires a shared protocol, and it currently has shared spellings by convention.** The parent, build script, helper, and cleaner each own some of `brokkr-launch`, `--plan`, `--probe`, the peer basename and `.brokkr-plan` suffix, the receipt suffix and contents, magic and tags, file-store names, and the plan-size formula. The 12 MiB + 64 KiB copies currently agree. The embedded bytes tie each parent to the helper it shipped, and the encoder fixtures and peer integration test catch some mismatches. The parent rejects nonabsolute peer executables, while the helper checks only that an executable is present. The helper also accepts repeated scalar tags as last-wins while rejecting duplicate environment entries. **Enforcement:** one dependency-free protocol source for both compilation units, including typed modes and shared limits. Add decoder rejection and round-trip tests across the real boundary. [Parent protocol](/home/folk/Programs/brokkr/src/launch/mod.rs:55) · [Helper parser](/home/folk/Programs/brokkr/src/launch/helper_main.rs:490) · [Peer mode](/home/folk/Programs/brokkr/src/launch/helper_main.rs:903) · [Peer writer](/home/folk/Programs/brokkr/src/launch/probed.rs:352) · [Cleaner](/home/folk/Programs/brokkr/src/maintenance.rs:50)
- **The receipt conflates helper arrival, exec, and Cargo exit status.** The helper reads `/proc/self/exe`, inspects arguments, constructs the receipt pathname, and opens it before writing `started`. Each can fail, so a missing receipt does not prove the helper never ran. The parent classifies any readable contents besides exactly `started\n` as failure and waives a missing receipt for Cargo's 101. If appending `failed` fails, a receipt can still say `started` after a helper failure. Runtime narration is printed before classification. **Enforcement:** typed handoff states with a distinct channel for setup failure, plus a transcript test for missing, partial, and failed handoffs. Exit 101 alone cannot distinguish a Cargo failure from another program returning the same code. [Helper dispatch](/home/folk/Programs/brokkr/src/launch/helper_main.rs:948) · [Receipt creation](/home/folk/Programs/brokkr/src/launch/helper_main.rs:840) · [Failure recording](/home/folk/Programs/brokkr/src/launch/helper_main.rs:194) · [Parent classification](/home/folk/Programs/brokkr/src/runnables.rs:328)
- **The static helper implements host process policy by hand.** It assumes Linux x86_64 or aarch64 syscall and startup-stack ABIs, readable `/proc/self/exe`, bounded paths and cwd, an executable filesystem under `HOME`, `/bin/sh`, and a glibc-style default `PATH`. It has its own PATH search, `ENOEXEC` fallback, and errno policy. It calls `getcwd` even when keeping cwd, and a removed helper can be reported by procfs with a basename that fails its mode check. The fixed arrays reserve roughly 66 MiB of address space before the working program starts. Missing procfs, a noexec home, a tight address-space limit, or a restricted syscall environment can fail a launch that its target could otherwise perform. The platform gate and ELF check live in separate places, and the test reads little-endian headers. **Enforcement:** one supported-platform declaration, a host capability check before building, build-time ELF validation, and cross-architecture process fixtures for PATH, cwd, and file execution. ## Install publication and filesystem authority

- **Cargo owns what it installs, while brokkr guesses what to stamp.** `install_root` copies the nonempty `CARGO_INSTALL_ROOT` and `install.root` rules conservatively, then forces `--root` or skips stamping. The manual describes any set `CARGO_INSTALL_ROOT`, while the code ignores an empty value. `installable_bins` supplies a lower and upper default-feature closure, refuses dependency-feature ambiguity, and feeds both `--names` and stamping. The same ambiguity fails `--names` but only warns after an actual install. Duplicate configured package entries are accepted and cause repeated install attempts. **Enforcement:** consume the resolved install plan and actual Cargo publication ledger. Until that exists, make the distinction between a prediction and a confirmed publication explicit in the type and test root and feature parity against Cargo. [Install root and names](/home/folk/Programs/brokkr/src/build_info.rs:80) · [Config admission](/home/folk/Programs/brokkr/src/config_parts/parser.rs:262) · [Install execution](/home/folk/Programs/brokkr/src/runnables.rs:738) · [Manual](/home/folk/Programs/brokkr/docs/commands/run.md:581)
- **Install can fail after changing the machine, and it has no command-level resume record.** It samples stamps and preflights copy steps early, but resolves each package's install root inside the publication loop, decides `--locked` from conventional `workspace_root/Cargo.lock`, and discovers `objcopy` and ELF errors after Cargo installs. A later package, stamp, or shell step can fail with earlier binaries already replaced. `stamp_file` refuses any existing stamp, and the caller does not distinguish a newly installed file from a successful Cargo invocation that leaves a binary in place. If Cargo leaves a stamped binary in place, rerunning reaches that refusal before post-install steps. **Enforcement:** preflight the resolved plan as a whole, stage and verify the binaries and stamps, then let an install backend publish and record completed steps. Test identical retries and failures at each publication boundary. General shell actions need an explicit idempotence or compensation contract. [Install ordering](/home/folk/Programs/brokkr/src/runnables.rs:774) · [Stamp refusal](/home/folk/Programs/brokkr/src/build_info.rs:210) · [Post-install semantics](/home/folk/Programs/brokkr/docs/commands/run.md:692)
- **Stamp replacement mutates Cargo's install tree using a different durability policy from copy installation.** Stamping makes PID/name scratch files in Cargo's `bin`, runs `objcopy`, checks the section, applies permissions, and renames over the original. It does not explicitly sync the file or directory, bind replacement to the file Cargo published, or preserve ownership and extended metadata as part of its contract. The normal error path removes scratch, but a killed process can leave it in another tool's directory. **Enforcement:** own inputs and intermediate files in a brokkr install staging area. Give a destination backend explicit authority over Cargo's install root and an exclusive same-filesystem publication slot. Verify binary identity and the metadata the backend promises before publication. [Stamp write](/home/folk/Programs/brokkr/src/build_info.rs:206) · [Stamp scratch](/home/folk/Programs/brokkr/src/build_info.rs:269) · [Durable writer](/home/folk/Programs/brokkr/src/atomic_write.rs:87)
- **Copy admits a lexical source and then operates on a resolved one.** Config rejects absolute paths, `.` and `..`, but an intermediate symlink can take `copy.from` outside the project. The runtime canonicalizes after observation and uses the result for overlap checks, without re-establishing source containment. For destinations, the layout intentionally follows symlinked parents, accepts arbitrary absolute targets, and guards overlaps using mostly pathname comparisons. A changed parent, mount alias, or case-folding filesystem can defeat some assumptions behind those comparisons. **Enforcement:** typed relative source and destination grants, descriptor-relative containment and identity checks, and real filesystem fixtures for symlinks, aliases, and case folding. [Config path checks](/home/folk/Programs/brokkr/src/config_parts/parser.rs:1600) · [Source admission](/home/folk/Programs/brokkr/src/install_step/mod.rs:256) · [Destination resolution](/home/folk/Programs/brokkr/src/install_step/mod.rs:497)
- **Install ownership is split between pathname policy, content evidence, and project name.** A registry owner is the project name and step name. Two checkouts with the same project and step can replace the same unchanged destination. Renaming either creates a foreign claim. Registry deserialization checks the version and lookup checks the filename, while recovery still trusts stored path roles, container names, fingerprint strings, and phase relationships that the writer established outside the type. **Enforcement:** validated journal records, typed destination and container identities, and a declared installation identity that survives checkout moves and step renames according to an explicit policy. - **The copy transaction has a strong publication primitive and weaker surrounding path operations.** Publication uses directory descriptors and atomic `renameat2`. Staging, fingerprinting, and cleanup later or earlier reopen paths by name. File hashing and staging each reproduce the no-follow open and device/inode check, while directory traversal and removal are path-based. `Allocated` recovery has no recorded container identity and assumes the reserved name is exclusive to brokkr. The docs explicitly require a quiescent destination and durable home. - **Host filesystem features are discovered during publication.** The copy backend requires working `renameat2` flags, directory `fsync`, stable directory identity, directory search and write permissions, and compatible Unix mode behavior. Its same-parent staging avoids the usual cross-filesystem rename, but a filesystem that rejects exchange, no-replace, or directory sync fails the copy after Cargo publication. Outside home, a parent created just before a crash can remain unsynced across retries, a failure the code and manual already identify.
